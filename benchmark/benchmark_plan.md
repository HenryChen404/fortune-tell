## 0. 全局规则

### 0.1 禁止 Web Research

**整个 benchmark 流程禁止使用任何搜索/联网工具。** 验盘和解盘过程中，输出必须纯粹基于算法和命理理论推导，不能通过搜索引擎查询测试人物的信息。

### 0.2 事件验证时间窗口

用于对照验证的人生事件必须发生在 **2025年5月之后、2026年6月20日之前**（模型 knowledge cutoff 之后），防止模型从训练数据中"知道"答案。

### 0.3 测试人物策略（方案 B）

使用**公开名人**作为测试人物，但事件验证仅限定 2025.5–2026.6 时间窗口内的事件。计算正确性（维度 A）不受此限制——纯数值对比不涉及模型知识。

## 1. 目标

从"有没有bug"升级到"每一步的输入输出是否符合预期"，建立 agent benchmark 式的端到端评估体系。

### 三个评估维度

| 维度 | 评估什么 | 类比 |
|------|---------|------|
| **A. 计算正确性** | 四个排盘脚本的数值输出是否与权威工具一致 | 类似 astrology API benchmark（对比 Swiss Ephemeris / Jagannatha Hora） |
| **B. 运行轨迹** | Skill 每一步的输入→输出是否符合 SKILL.md 定义的流程 | 类似 AgentBench 的 trajectory evaluation（参考 AgentProcessBench 三元标注法） |
| **C. 解读质量** | 验盘预测的具体性、三大法则的遵守、交叉验证的正确性 | 类似 LLM-as-judge 评估 + 真人命理师对照 |

### 评分方法论

参考 AgentProcessBench 的三元标注法，每个评估点采用 **+1 / 0 / -1** 评分：

| 分数 | 含义 | 示例 |
|------|------|------|
| **+1** | 完全正确 | 行星经度差 ≤0.05°；步骤输入输出完全符合 SKILL.md |
| **0** | 部分正确/无法判断 | 行星星座正确但度数偏差 0.1-0.5°；步骤产出基本合理但有遗漏 |
| **-1** | 错误 | 四柱天干地支不一致；步骤逻辑错误或跳过必要流程 |

**错误传播规则**：关键步骤（如 Step 1.4 排盘）的 -1 会影响下游步骤评分——下游步骤即使执行正确但使用了错误输入，最多评 0 分。

## 2. 维度 A：计算正确性 Benchmark

### 2.1 方法论

参考业界做法（VedIntel vs Jagannatha Hora, RoxyAPI vs NASA JPL DE441, BeyondBazi 的 Li Chun 规范），用**权威在线工具的输出**作为 ground truth，对比我们脚本的输出。

### 2.2 Ground Truth 来源

| 体系 | Ground Truth 工具 | 验证精度 |
|------|------------------|---------|
| 八字 BaZi | BeyondBazi.com / BaziLabs.com / 元亨利贞网 | 四柱天干地支完全一致；十神一致；大运起始年龄±1年 |
| 紫微 ZiWei | 紫微斗数排盘网 / iztro 官方示例 | 命宫主星一致；十二宫安星一致；四化一致 |
| 西洋 Western | astro.com (Extended Chart) | 行星经度 ±0.05°；ASC ±0.5°（ASC 对时间高度敏感，放宽容差）；宫位行星一致 |
| 吠陀 Vedic | Jagannatha Hora (JHora) / Drik Panchang | Lagna 星座一致；行星经度 ±0.05°；Dasha 起始 ±2天 |

**容差说明**：
- 行星经度 ±0.05°：行星运行缓慢，不同星历表差异极小
- ASC ±0.5°：上升点每4分钟移动约1°，对出生时间的秒级精度敏感，故容差放宽至 ±0.5°
- Dasha ±2天：不同软件对 Ayanamsa 的微小差异会导致月亮精确度数不同，影响 Dasha 计算

### 2.3 测试用例矩阵

**5 个标准测试人物**（覆盖不同时区、年代、性别）：

| # | 身份 | 出生数据 | 选择原因 |
|---|------|---------|---------|
| T1 | 标准北京男 | 1995-03-15 14:30, 北京(39.9,116.4), 男 | 现有测试数据，有完整参考 |
| T2 | 标准上海女 | 1988-06-15 08:30, 上海(31.2,121.5), 女 | DST 时代、女性大运方向 |
| T3 | 美东出生 | 2000-01-01 00:05, 纽约(40.7,-74.0), 男 | 西半球（注意负经度）、千禧年边界、午夜 |
| T4 | 时辰边界 | 1990-08-20 22:55, 成都(30.6,104.1), 女 | 时辰边界(亥/子)、西部城市(经度差大) |

### 2.4 中间值验证

除最终输出对比外，对以下**中间计算步骤**进行验证：

| 验证项 | 测试用例 | 预期 | 验证方式 |
|--------|---------|------|---------|
| 真太阳时转换 | T3 (纽约, 经度-74.0) | 真太阳时与当地平太阳时的差值合理（±15分钟内） | 对比公式计算或在线工具 |
| 真太阳时转换 | T4 (成都, 经度104.1) | 经度差导致的时间修正约 -63.6分钟（(120-104.1)×4） | 检查 bazi 输出的真太阳时字段 |
| 负经度处理 | T3 | 西洋/吠陀脚本正确传入 lng=-74.0，八字/紫微使用 -74.0 进行真太阳时校正 | 检查脚本参数和输出 |

### 2.6 执行流程

```
对每个测试人物 T:
  1. 运行我们的 4 个脚本，保存输出
  2. 在 ground truth 工具中输入相同数据，截图/记录输出
  3. 逐项对比，记录：+1(MATCH) / 0(PARTIAL) / -1(MISMATCH)
  4. 中间值验证：检查真太阳时、负经度处理等
  5. 汇总：匹配率、不匹配项分析、错误传播标注
```

## 3. 维度 B：运行轨迹 Benchmark

### 3.1 方法论

参考 AgentProcessBench 的 trajectory evaluation + 三元标注法（+1/0/-1）：不只看最终结果，还评估每一步是否正确，并追踪错误传播。

### 3.2 Skill 执行步骤分解

根据 SKILL.md + calibration_guide.md + reading_guide.md + natal_pet_guide.md，完整的 skill 执行分为以下步骤：

```
Phase 0: 启动
├── Step 0.1: 权限预配置检查（15个权限模式完整性验证）
│   验证清单：
│   Bash(python3.11:*), Bash(node:*), Bash(git:*), Bash(which:*),
│   Bash(ls:*), Bash(mkdir:*), Bash(mv:*), Bash(cd:*),
│   Bash(npm install:*), Bash(pip3:*), Bash(python3.11 -m pip:*),
│   Bash(echo:*), Bash(SCRIPTS=:*), Bash(REFS=:*), Bash(PROFILE=:*)
├── Step 0.2: 更新检查 (git fetch + log)
├── Step 0.3: 数据目录初始化 (mkdir -p)
├── Step 0.4: 依赖检查 (python3.11, node, packages)
└── Step 0.5: 档案扫描 (ls profiles/*)

Phase 1: 用户交互 & 排盘
├── Step 1.1: 问候 + Banner 展示
├── Step 1.2: 收集出生信息（称呼、日期、时间、性别、出生地）
├── Step 1.3: 推算经纬度和时区（不向用户询问）
├── Step 1.4: 四脚本并行执行
│   ├── bazi_chart.py → bazi.md
│   ├── ziwei_chart.js → ziwei.md
│   ├── western_chart.py → western-astrology.md
│   └── vedic_chart.py → vedic-astrology.md
├── Step 1.5: 保存 birth-info.md
└── Step 1.6: 展示命盘宠物预览卡
    ├── 调用 natal_pet_card.py --mode preview
    ├── 验证：输出卡牌名、R级别
    └── 验证：维罗妮卡口吻引出（"排盘完成了，顺便给你看看..."）

Phase 2: 验盘
├── Step 2.0: 排盘预检
│   ├── DST检测（1986-1991年出生 + 中国 → 必须询问）
│   ├── 时辰边界检测（真太阳时±15分钟）
│   └── 公历/农历确认
├── Step 2.1: 读取 4 个命盘文件
├── Step 2.2: 取象（原局象 + 格局组合 + 先天强弱）
│   每体系≥2个原局象，含先天强弱标注(强/中/弱)
├── Step 2.3: 列出时间段（八字大运、紫微大限、吠陀Dasha、西洋行运）
├── Step 2.4: 推运断事 → 生成预测选项
│   验证：具体事件（非性格描述），有时间锚点
├── Step 2.5: 标注探测类型 + 按时期分组
│   探测类型：time_diagnostic, form_probe, magnitude_probe
├── Step 2.6: 写入 calibration_plan.md
│   覆盖要求验证：
│   - 总选项 15-20 个（Tier 1: 10-14, Tier 2: 5-6）
│   - Tier 1 中至少 3-4 个 time_diagnostic
│   - 每个体系至少 2 个 form_probe
│   - 先天强弱"强"的原局象含 magnitude_probe
│   - 每个选项有 (原局象×时期) 激发推导
│   - 每个选项是具体事件，不是性格描述
│   - 来源标注完整
├── Step 2.7: 呈现 Tier 1（AskUserQuestion，每组2-4项）
├── Step 2.8: 收集反馈 + Round 2 追问
│   Round 2 完整性验证：
│   - 每条未选中选项都必须追问（不跳过、不默认）
│   - 追问使用自然对话（非AskUserQuestion）
│   - 四种反馈场景正确分类：
│     完全对不上 / 象对事不同 / 方向对程度不同 / 完全对上
├── Step 2.9: 时辰校正（条件触发：60%+ contradicted）
│   S2场景验证：
│   - 收集3-5个重大事件
│   - 推算2-3个候选时辰
│   - 重新排盘 + 新验盘预测
│   - 与命主确认新预测
├── Step 2.10: 保存验盘档案 + 基准线分析
│   验盘档案格式验证：confirmed/confirmed_form/confirmed_scaled/contradicted
└── Step 2.11: 收尾 → 过渡到解盘（含命盘宠物进化展示）

Phase 3: 解盘
├── Step 3.1: 读取 birth-info + 判断适用体系（第一法则：≥2体系）
├── Step 3.2: 读取命盘 + 验盘档案 + 基准线
├── Step 3.3: 逐体系分析
│   - 方向选择依据验盘结果（confirmed/contradicted/tier2_skipped）
│   - 篇幅语气匹配先天强弱（经基准线修正）
│   - 措辞确定性匹配置信度
├── Step 3.4: 交叉比对（第二法则：高共识过滤）
│   只输出≥(a-1)个体系一致的结论
├── Step 3.5: 古今映射（第三法则）
│   无直接引用古代社会场景
└── Step 3.6: 输出（子问题拆解、结构化回答）
```

### 3.3 Trace 评估方法

为每个步骤定义**输入、预期输出、评估标准**，采用 +1/0/-1 三元评分：

| Step | 输入 | 预期输出 | +1 条件 | 0 条件 | -1 条件 |
|------|------|---------|--------|--------|---------|
| 0.1 | settings.local.json | 权限检查结果 | 正确识别15个权限模式的完整性 | 检查了但遗漏部分权限 | 跳过检查或检查逻辑错误 |
| 1.3 | 城市名"北京" | lat=39.9, lng=116.4, tz=Asia/Shanghai | 经纬度±0.5°, 时区正确 | 经纬度±1°或时区偏移有误 | 完全错误或向用户询问 |
| 1.4 | 出生数据 | 4个.md文件 | 4文件并行执行，存在且非空，格式正确 | 串行执行或部分格式问题 | 文件缺失或执行失败 |
| 1.6 | ziwei.md | 命盘宠物预览卡 | 调用preview模式，展示卡牌名+R级，维罗妮卡口吻 | 调用了但展示不完整 | 跳过或调用错误模式 |
| 2.0 | birth-info | 排盘预检结果 | DST/边界/历法全检，写入birth-info.md | 部分检查 | 跳过预检 |
| 2.2 | 4个命盘 | 原局象清单 | 每体系≥2个原局象，含先天强弱标注 | 部分体系遗漏或强弱标注不全 | 未做取象或严重错误 |
| 2.4 | 原局象×时段 | 预测选项 | 具体事件(非性格)，有时间锚点，独立拆分 | 事件但锚点模糊 | 性格描述或无时间锚 |
| 2.6 | 预测选项 | calibration_plan.md | 满足全部覆盖要求(数量+探测类型+来源) | 部分满足 | 未写入或严重不足 |
| 2.8 | Round 1结果 | Round 2 追问 | 每条未选中都追问，正确分类四种场景 | 追问了多数但跳过少数 | 大量跳过或分类错误 |
| 3.4 | 多体系分析 | 高共识筛选 | 只输出≥(a-1)体系一致的结论 | 阈值略偏但方向正确 | 输出不一致结论或未做比对 |

### 3.4 模拟测试场景

设计 **3 个端到端模拟场景**，用固定的用户回答来测试完整轨迹：

| 场景 | 用户画像 | 模拟回答策略 | 测试重点 |
|------|---------|------------|---------|
| **S1: 新用户全流程** | 首次使用，名人出生数据 | 验盘全部配合回答（70%+ confirmed） | 完整流程执行顺序，每步输入输出，natal_pet preview |
| **S2: 验盘校正** | 时辰不确定的名人 | 60%+ contradicted → 触发时辰校正 | 时辰校正流程（收集3-5重大事件→推2-3候选时辰→重排→新预测→确认） |
| **S3: 回访用户** | 已有档案，距上次验盘>1年 | 直接解盘 + 增量验盘触发检查 | 档案加载、解盘质量、增量验盘触发条件判断 |

**S3 增量验盘说明**：如果距上次验盘已超过1年且有新的大运/大限/Dasha进入，应考虑是否需要增量验盘以更新基准线。

每个场景记录完整 trace：
```
Step | Input | Expected Output | Actual Output | Score(+1/0/-1) | Error Propagation | Notes
```

## 4. 维度 C：解读质量 Benchmark

### 4.1 方法论

结合 LLM-as-judge 自动评估 + 真人命理师对照，采用锚定评分量表。

### 4.2 评分量表（0/1/2 锚定）

| 维度 | 0 分 | 1 分 | 2 分 |
|------|------|------|------|
| **预测具体性** | 性格描述（"你容易焦虑"） | 有事件但模糊（"经历过变化"） | 具体事件+时间锚（"2023年搬过家"） |
| **时间锚定** | 无时间段 | 有年代但不精确 | 精确到年份或年龄段 |
| **三法则遵守** | 违反任一法则 | 基本遵守但有模糊处 | 严格遵守且清晰标注 |
| **术语控制** | 暴露内部术语 | 偶有术语但及时解释 | 零术语，纯自然语言 |
| **矛盾处理** | contradicted未降权 | 降权但处理不够细致 | 严格按规则分场景处理 |
| **基准线应用** | 未使用基准线 | 使用但修正不够 | 强度措辞完全匹配先天强弱+基准线 |

### 4.3 验盘数据利用量化

除定性评估外，需量化验证解盘是否正确利用了验盘数据：

| 检查项 | 通过标准 |
|--------|---------|
| confirmed 条目 → 解盘中出现 | 覆盖率 ≥ 90% |
| confirmed_form 条目 → 按锁定形式 | 一致率 = 100% |
| confirmed_scaled 条目 → 基准线修正 | 修正方向正确率 ≥ 80% |
| contradicted 条目 → 降权处理 | 降权率 = 100% |
| tier2_skipped 条目 → 中置信度+注明 | 标注率 ≥ 80% |

### 4.4 Ground Truth：真人命理师对比

分两阶段进行：

**Phase 3a（先行）：公开名人案例**
- 选择有公开八字/紫微分析的名人（如知名命理频道、公开教学案例）
- 对比我们的 skill 产出与专业命理师的公开分析
- 对比维度：原局象提取覆盖率、关键时间节点一致性、大运分析方向

**Phase 3b（条件具备时）：真人专家邀请**
- 邀请 1-2 位真人命理师对同一命盘出具简要分析
- 对比：
  - 原局象提取的覆盖度（skill 提取 vs 人工提取的重叠率）
  - 验盘预测的命中方向（skill 预测 vs 专家预测的一致性）
  - 大运分析的关键时间节点是否一致

### 4.5 评估 Checklist（每次解盘）

```markdown
## 解盘质量检查

### 第一法则：可答性
- [ ] 明确标注适用体系数量
- [ ] 不适用的体系未参与解盘
- [ ] 只有1个体系适用时拒绝解盘

### 第二法则：高共识
- [ ] 只输出≥(a-1)个体系一致的结论
- [ ] 不一致的点未输出但告知用户
- [ ] 完全分歧时坦诚告知

### 第三法则：古今映射
- [ ] 古代概念已映射到现代语境
- [ ] 无直接引用古代社会场景

### 验盘数据利用（量化）
- [ ] confirmed → 高权重（覆盖率 ≥90%）
```

## 5. 执行计划

### Phase 1: 计算正确性（预计 2-3 天）

1. 为 5 个测试人物，在各 ground truth 工具中获取标准输出
2. 运行我们的脚本，逐项对比
3. 中间值验证（真太阳时、负经度）
4. 生成 130+ 项对比报告，标注所有 MISMATCH
5. MISMATCH 提交给 @Review-man 分析 → @Debug-man 修复

### Phase 2: 运行轨迹（预计 2-3 天）

1. 设计 3 个模拟场景的详细脚本（含固定用户回答，事件限定 2025.5-2026.6 窗口）
2. 手动执行（或用 Claude 模拟），记录每步 trace
3. 对比 trace 与 SKILL.md 定义的预期流程
4. 标注偏差（+1/0/-1），追踪错误传播
5. 提交报告

### Phase 3: 解读质量（预计 1-2 天）

1. Phase 3a: 收集公开名人命理分析作为参照
2. 用已有的测试档案执行解盘
3. 按 checklist + 0/1/2 量表逐项检查
4. 量化验盘数据利用率
5. Phase 3b（条件具备时）：真人专家对比
6. 生成质量报告
